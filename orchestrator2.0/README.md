# 业务变更影响分析 · Python 编排服务

从 Dify 工作流完整迁移而来：**全部流程逻辑在 Python，智能体平台只当 LLM 算力**
（平台侧工作流仅 开始→LLM→回复 三节点，双入参：指令 + 上下文）。

## 架构

```
浏览器 ──SSE──> server.py (5200)
                 └─ pipeline.py 编排（意图→分支→搜索→证据→分析→存状态）
                     ├─ store.py   图工具+存储（复用 gateway.py 的
                     │             Galaxybase 客户端 / history.db / <think> 过滤器）
                     ├─ prompts.py 全部提示词（改话术只改这里）
                     ├─ llm.py     LLM 算力层（dify 本地测试 / sfm 生产，可界面切换）
                     └─ settings.py 运行时配置（页面「系统配置」→ 实时生效）
```

**设计原则：确定性层与 LLM 层严格分工**——搜索定位、证据查询、去重、方向
分桶、序号解析全部由代码完成（零误差）；LLM 只做意图理解和组织语言。
影响分析的每一条结论（候选/系统/证据路径）都是代码预计算后交给 LLM 照抄。

## 文件

| 文件 | 职责 | 什么时候改它 |
|---|---|---|
| `server.py` | Flask 入口 + 全部 HTTP 接口 | 加接口 |
| `pipeline.py` | 对话主流程（四分支+影响分析） | 改流程/分支 |
| `prompts.py` | 全部提示词 | 改话术/输出格式 |
| `llm.py` | LLM 双平台后端 | 换平台/改调用方式 |
| `store.py` | 图工具 + 实体类型参数表 + 证据查询 | 改查询深度/搜索范围 |
| `gateway.py` | Galaxybase 客户端（含纯标准库 RSA 登录加密）+ SQLite 存储 + 图结构 | 改 GALAXY_* 默认连接配置 |
| `settings.py` | 运行时配置读写与热生效 | 加配置项 |
| `config.py` | 默认配置 + config.get() | 首次部署兜底值 |
| `runtime_config.json` | 界面保存的运行时配置（含密钥，勿外传） | 不手改 |

`gateway.py` 由旧根目录网关 app.py 融合而来（平台转发链路已删除），
其 GALAXY_* 配置由 settings.py 运行时覆盖。

## 核心流程

```
用户消息
  ├─ chat    闲聊/关于图谱系统的问题 → 通用回答（注入实时数据概况）
  ├─ fact    事实/清单类（涉及哪些系统/部门/子项…）→ 直答，不套报告模板
  ├─ targeted 已选定业务（含序号选择/追问）→ 直接影响分析
  └─ search  新业务 → 候选搜索（业务两类优先，全类兜底，2字滑窗模糊兜底）
               0 个→未找到 / 1 个→直接分析 / 多个→带序号清单等选择

影响分析（任意实体类型，含表/系统/部门…）：
  证据查询（确定性三段：1跳邻接 + 传播入边变长 + 子结构；
           非业务实体自动归并到业务再跑 6 跳依赖传播）
  → 代码分桶：受影响候选(直接/间接，连带承载系统+证据路径) /
     上游依赖 / 按角色关联（来源子项/承载业务/主管业务…）
  → LLM 排版为《变更影响分析报告》（对象/影响面表格/关联范围带路径/建议）
```

## 启动

```bash
cd 项目根目录
./start.sh                         # 自动挂离线依赖，py2 优先
# 或：cd orchestrator2.0 && python server.py
# 页面: http://<本机IP>:5200
```

依赖仅 `flask` + `requests` + 标准库，python 2.7 / 3.x 双兼容，
离线包 offline/ 已含全部依赖。

## 配置（页面左下「⚙ 系统配置」，保存即生效）

- 图数据库：地址 / 账号 / 密码 / 图名称（graphName）
- LLM 平台：本地测试平台（地址+Key）↔ 本地智能体平台（网关+APP_KEY+智能体编码），下拉切换
- 密钥回传掩码、留空=不修改；配置存 `runtime_config.json`

### 平台侧工作流怎么建（一次性）
1. 开始节点双入参：`query`（用户输入/上下文）+ `metadata`（角色指令）；
2. LLM 节点：系统提示词绑定 `metadata`（Dify）或平台等价变量（SFM 的
   message.metadata.prompt），用户消息绑定 `query`，**关闭思考模式**；
3. 回复节点输出 LLM 文本。（llm.py 对 Dify 自动兼容 workflow/chatflow 两种类型）

## 数据与维护

- 对话历史/业务状态：`orchestrator2.0/history.db`，删库即清空
- 图结构语义（影响传播规则/类型角色/关系含义/查询示例）：
  `orchestrator2.0/schema_notes.json` —— 这是分析质量的"深度控制器"，按业务确认维护
- 新增图实体类型：图导入后，schema_notes 的 entity_roles 加一条语义标注即可，
  代码零改动（未标注类型自动按 1 跳关联处理）
